文書作成ガイド
==============

Atlas のドキュメントは、運用中のホストで何を確認し、どこを変更し、失敗時にどこへ戻ればよいかを短く示すための文書です。
宣伝文や背景説明を厚くするより、作業者がそのまま使える判断材料を優先します。

基本方針
--------

本文は日本語で書きます。
コマンド、設定キー、ファイルパス、Python API 名、エラーメッセージは原文のまま ``literal`` として示します。
コード、コメント、docstring、commit message は英語で書きます。

文を足すときは、次の順で確認します。

* その説明が実装や設定ファイルから確認できるか。
* 読者が次に実行するコマンド、編集するファイル、確認するログが分かるか。
* 「安全」「簡単」「柔軟」などの評価語だけで終わっていないか。
* 同じ内容を README、Sphinx docs、CLI 出力のどこに置くべきか。

文体
----

Atlas の文体は、落ち着いた技術文書に寄せます。
強い断定は、実装や検証で裏づけられる場合だけ使います。
不確かな運用条件は「ホスト側で確認します」「事前に準備します」のように、責任の境界を明確にします。

避ける表現:

* 「とても」「広く」「なめらかに」など、動作を説明しない強調。
* 「これにより、より良い体験を提供します」のような一般論。
* 同じ見出し構造を各ページで機械的に繰り返すこと。
* 英語の直訳調で長くなる「できます」で足りる表現や、論点をぼかす言い回し。

推奨する書き方:

* 「``atlas scripts update`` は有効な設定済みリリースを更新します。」
* 「pyenv と Python build に必要な OS パッケージは Atlas の外で準備します。」
* 「コマンド名が衝突した場合、Atlas は shim 生成と実行を止めます。」

Shibuya での構成
----------------

Sphinx theme は ``shibuya`` を使います。
テーマは dev 依存に入れ、``docs/conf.py`` の ``html_theme`` で指定します。
フォントやヘッダーの調整は、Shibuya の partial template を使って ``docs/_templates`` 以下に置きます。

ナビゲーションは最小限にします。
上部ナビゲーションは、初めて読む人が最初に使うページだけに絞ります。
詳細なページ構造は左サイドバーの toctree に任せます。

ページ単位の目安
----------------

``concepts`` は設計境界を説明します。
使い方の手順や長い設定例は置かず、Atlas が何をしないかも明記します。

``usage`` はコマンドを実行する順番を示します。
例はコピーして使える形にし、前提条件は直前に書きます。

``configuration`` は設定ファイルの形と型制約を扱います。
サンプル YAML は最小構成と複数リリース構成を分けます。

``script-releases`` はリリース作者向けです。
``VERSION``、``release.yml``、``commands/``、``modules/``、requirements、ログの扱いをまとめます。

``operations`` は本番ホストでの確認順です。
障害時の説明は、症状から確認コマンドへ進める構成にします。

仕上げ確認
----------

公開前に次を確認します。

* ``python -m sphinx -W -b html docs docs/_build/html`` が通る。
* 新しいページが ``docs/index.rst`` の toctree に入っている。
* 未完了の作業メモを本文に残していない。
* 文書内の用語が揺れていない。特に ``runtime``、``scripts venv``、``release``、``shim`` は統一する。
* 日本語が過度に整いすぎていない。必要なら `ja-writing-humanizer <https://github.com/viasnake/ja-humanizer>`_ の観点で、意味を変えずに局所的に推敲する。
